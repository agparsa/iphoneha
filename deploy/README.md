# استقرار iphoneha.com روی سرور

این پوشه همهٔ چیزی است که برای بالا آوردن سایت روی سرور فعلی لازم است.

**سرور:** `srv1883916.hstgr.cloud` — VPS هاستینگر، AlmaLinux 10، cPanel 138، IP: `2.25.204.68`
**نکتهٔ مهم:** روی این سرور سه سایت زندهٔ دیگر هم هست (`isarnamad.com`، `nogrehland.ir`، `devopss.ir`). هیچ‌کدام از دستورهای این راهنما سراسری نیست؛ همه فقط `iphoneha.com` را لمس می‌کنند.

## معماری

```
اینترنت
  │
  ├─ :443  nginx (cPanel)
  │        ├─ /api/*, /_next/*, /media/*  ─────────────►  Node مستقیم (بدون Apache)
  │        └─ بقیهٔ مسیرها ─► :444 Apache ─► 127.0.0.1:3000  Next.js
  │                                                │
  │                                                └─► 127.0.0.1:4000  NestJS API
  │                                                        ├─ 127.0.0.1:55432  PostgreSQL (Docker)
  │                                                        └─ 127.0.0.1:56379  Redis (Docker)
```

- PostgreSQL و Redis داخل کانتینرند، چون `redis` در مخزن CloudLinux 10 وجود ندارد و نمی‌خواهیم روی سروری که سه سایت زنده دارد پکیج سیستمی اضافه کنیم. هر دو فقط روی `127.0.0.1` باز هستند.
- کانتینرها با `network_mode: host` اجرا می‌شوند و مستقیم روی loopback گوش می‌دهند (`listen_addresses=127.0.0.1` و `--bind 127.0.0.1`). دلیلش فایروال **CSF** روی این سرور است: اتصال خروجی میزبان به شبکهٔ bridge داکر را رد می‌کند و پورت منتشرشده اتصال را می‌پذیرد ولی هیچ‌وقت جواب نمی‌دهد (Prisma: `P1001`). ترافیک loopback را CSF همیشه عبور می‌دهد، پس به تنظیمات فایروال دست زده نمی‌شود.
- روی همین سرور کانتینرهای پروژهٔ دیگری هم هست (`trading-platform-prod-*`). هیچ‌کدام از دستورها Docker را ری‌استارت نمی‌کند و فقط دو کانتینر `iphoneha-*` را می‌سازد یا عوض می‌کند.
- API و Next.js مستقیم با Node 22 خود سرور اجرا می‌شوند (systemd)، نه داخل داکر — سبک‌تر و بیلدش روی ۲ هسته سریع‌تر است.
- API روی `127.0.0.1` گوش می‌دهد، پس از بیرون مستقیماً در دسترس نیست.

## راه سریع از گیت‌هاب (پیشنهادی)

ریپو در گیت‌هاب: **private** بساز (سورس فروشگاه است). روی سرور با **root**:

```bash
git clone https://github.com/USERNAME/iphoneha.git /home/iphoneha/app
bash /home/iphoneha/app/deploy/bootstrap-root.sh
```

برای ریپوی private، `git clone` نام کاربری و به‌جای رمز یک **Personal Access Token** می‌خواهد (GitHub → Settings → Developer settings → Fine-grained tokens → فقط دسترسی Contents: Read روی همین ریپو). توکن را روی سرور تایپ کن، هیچ‌جای دیگر.

به‌روزرسانی‌های بعدی:

```bash
cd /home/iphoneha/app && git pull && bash deploy/bootstrap-root.sh
```

## راه سریع: یک دستور (بدون گیت)

فایل `iphoneha-deploy.tar.gz` را در cPanel → File Manager داخل `/home/iphoneha/` آپلود کن، بعد با **root**:

```bash
tar xzf /home/iphoneha/iphoneha-deploy.tar.gz -C /tmp iphoneha/deploy/bootstrap-root.sh --strip-components=2
bash /tmp/bootstrap-root.sh
```

همین. اسکریپت سورس را باز می‌کند، `.env` را با رمزهای تصادفی می‌سازد، با کاربر `iphoneha` بیلد می‌گیرد، سرویس‌ها و پروکسی را نصب می‌کند و در آخر تست می‌کند. اگر هر مرحله‌ای شکست بخورد، همان تغییر را برمی‌گرداند و علتش را چاپ می‌کند.

مراحل زیر همان کار را دستی و قدم‌به‌قدم توضیح می‌دهند.

cd /home/iphoneha/app

# سه رمز تصادفی بساز و جای CHANGE_ME بگذار

کاربر cPanel به سوکت داکر دسترسی ندارد، پس کانتینرها را root بالا می‌آورد:

## مرحله ۴ — بیلد (با root، ولی اجرا با کاربر `iphoneha`)

```bash
cd /home/iphoneha/app
systemd-run --quiet --wait --pipe --collect --uid=iphoneha --gid=iphoneha \
  --working-directory=/home/iphoneha/app \
  -p MemoryHigh=2G -p MemoryMax=2560M -p MemorySwapMax=0 -p CPUQuota=150% -p IOWeight=50 \
  /bin/bash -lc ./deploy/deploy.sh </dev/null
```

**چرا با `su` اجرا نمی‌شود:** روی CloudLinux، نشست `su` داخل LVE حساب می‌رود و روی این سرور سقف آن ۱ گیگابایت رم و ۱ مگابایت بر ثانیه دیسک است. `next build` حدود ۱٫۸ گیگابایت لازم دارد و آنجا با `Killed` بسته می‌شود. `systemd-run` همان کاربر بدون دسترسی root را در یک cgroup جدا با سقف مشخص اجرا می‌کند؛ این سقف را طوری گذاشته‌ام که سایت‌های دیگر سرور هم رم و CPU کافی داشته باشند. `bootstrap-root.sh` همین کار را خودش انجام می‌دهد.

(اسکریپت خودش pnpm را در صورت نبود، داخل `$HOME` نصب می‌کند — نیازی به root نیست. با داکر هم کاری ندارد؛ فقط منتظر می‌ماند تا پورت‌های ۵۵۴۳۲ و ۵۶۳۷۹ جواب بدهند.)

این اسکریپت: منتظر دیتابیس و ردیس می‌ماند، وابستگی‌ها را نصب می‌کند، API را بیلد می‌کند، مهاجرت‌ها را اجرا می‌کند، اگر کاتالوگ خالی بود seed می‌زند، API تازه را بالا می‌آورد و **بعد** فروشگاه را روی همان API بیلد می‌کند (صفحه‌ها موقع بیلد از API خوانده می‌شوند، پس ترتیب مهم است) و در آخر سرویس‌ها را ری‌استارت می‌کند.

روی ۲ هسته، اولین بیلد حدود ۵ تا ۱۰ دقیقه طول می‌کشد.

## مرحله ۷ — راه‌اندازی برای مشتری واقعی (یک بار)

```bash
bash /home/iphoneha/app/deploy/go-live.sh
```

اسکریپت این اطلاعات را **همان‌جا در ترمینال** می‌پرسد و آن‌ها هیچ‌جای دیگری فرستاده نمی‌شوند:

- موبایل شما (مدیر اصلی)
- تلفن عمومی سایت
- نام کاربری و رمز وب‌سرویس ملی‌پیامک و bodyId الگوها
- مرچنت‌کد زرین‌پال

بعد از آن:

- مدیرهای نمونه غیرفعال می‌شوند.
- امتیازهای ساختگی و کد تخفیف نمونه حذف می‌شوند.
- موجودی محصولات نمونه صفر می‌شود. این کار فقط یک بار انجام می‌شود و اجرای دوباره هرگز موجودی واقعی را پاک نمی‌کند.
- سایت ری‌استارت می‌شود و هر دو کلید واقعاً آزمایش می‌شوند: یک پیامک کد ورود به موبایل شما می‌رود و از زرین‌پال یک پرداخت آزمایشی باز می‌شود که هیچ مبلغی از آن کسر نمی‌شود.

الگوهای ملی‌پیامک در خط خدماتی اشتراکی باید از قبل تأیید شده باشند:

| الگو             | متن پیشنهادی                                         | متغیرها                      |
| ---------------- | ---------------------------------------------------- | ---------------------------- |
| ورود (الزامی)    | `آیفونی‌ها` ⏎ `کد ورود شما: {0}`                     | `{0}` کد                     |
| پرداخت (اختیاری) | `آیفونی‌ها` ⏎ `پرداخت سفارش {0} با موفقیت انجام شد.` | `{0}` شمارهٔ سفارش           |
| ارسال (اختیاری)  | `آیفونی‌ها` ⏎ `سفارش {0} ارسال شد. کد رهگیری: {1}`   | `{0}` سفارش، `{1}` کد رهگیری |

**پرداخت‌های شبیه‌سازی‌شده در production هرگز فعال نمی‌شوند.** روشی که درایورش `mock` است نه در سایت نمایش داده می‌شود و نه از API پذیرفته می‌شود. صفحهٔ درگاه آزمایشی هم ۴۰۴ می‌دهد. سرویس‌های اقساطی آنلاین تا وقتی با کلید اصلی وصل نشده‌اند (بخش «خرید قسطی آنلاین» پایین‌تر)، در هیچ جای سایت تبلیغ نمی‌شوند و به‌جای آن‌ها خرید با چک و سفته نمایش داده می‌شود.

**زرین‌پال چطور تأیید می‌شود.** سفارش فقط وقتی «پرداخت‌شده» می‌شود که `verify` زرین‌پال همان authority را تأیید کند که سایت برای همان پرداخت باز کرده بود. authority داخل آدرس بازگشت فقط وقتی حساب می‌شود که با authority ذخیره‌شده یکی باشد، پس پرداخت یک سفارش دیگر (یا پرداختی به همین مرچنت بیرون از سایت) هیچ سفارشی را پرداخت‌شده نمی‌کند. اگر مشتری پول را داده ولی به سایت برنگشته، قبل از لغو سفارش وضعیتش از زرین‌پال پرسیده و `verify` می‌شود، چون پولی که `verify` نشود زرین‌پال به خریدار برمی‌گرداند.

### ورود به پنل وقتی پیامک نمی‌رسد

تا وقتی الگوی ملی‌پیامک تأیید نشده یا پیامک از سرور نمی‌رود، کد ورود مدیر را خود سرور نشان می‌دهد:

1. در `https://iphoneha.com/admin/login` موبایل را وارد کن و «ارسال کد» را بزن.
2. با **root**: `bash /home/iphoneha/app/deploy/admin-code.sh 09121234567`
3. کدی که چاپ می‌شود را به‌جای کد پیامکی وارد کن. کد ۱۰ دقیقه و فقط یک بار معتبر است.

فقط شمارهٔ یک مدیر فعال کد می‌گیرد و کد فقط در همین ترمینال چاپ می‌شود. مشتری‌ها این راه را ندارند و تا پیامک درست نشود نمی‌توانند وارد شوند.

### سرویس‌های ایرانی از سرور خارج (Iranian services from a server abroad)

این سرور (`2.25.204.68`) در دیتاسنتر Hostinger در بوستونِ آمریکاست. مرورگر مشتری مستقیم به درگاه زرین‌پال می‌رود و این بخش مشکلی ندارد. ولی ساختن تراکنش، `verify` و پیامک از خود سرور فرستاده می‌شوند و بعضی سرویس‌های ایرانی به IP خارج از ایران جواب نمی‌دهند. اگر `go-live.sh` نوشت `got no answer` یا زرین‌پال خطای `-10` داد، این راه‌ها هست:

| راه                        | توضیح                                                                                                                                                             |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| لیست IP مجاز زرین‌پال      | اگر در پنل زرین‌پال برای ترمینال IP مجاز تعریف شده، `2.25.204.68` را اضافه کنید و `go-live.sh` را دوباره اجرا کنید                                                |
| سرور یا هاست داخل ایران    | پایدارترین راه برای فروشگاه ایرانی است. سایت در قطعی اینترنت بین‌الملل هم برای مشتری ایرانی باز می‌ماند. همین بسته روی یک VPS مشابه (cPanel و Docker) نصب می‌شود  |
| یک سرور کوچک واسط در ایران | سایت همین‌جا می‌ماند و فقط درخواست‌های زرین‌پال و ملی‌پیامک از یک VPS ایرانی رد می‌شوند. برای این کار یک تنظیم کوچک در کد لازم است که هر وقت لازم شد اضافه می‌شود |

`go-live.sh` را هر چند بار که لازم باشد می‌شود دوباره اجرا کرد. پاک‌سازی داده‌های نمونه فقط بار اول انجام می‌شود.

### فقط پیامک (بدون زرین‌پال)

برای وصل کردن ملی‌پیامک پیش از گرفتن مرچنت‌کد زرین‌پال، با root:

```bash
bash /home/iphoneha/app/deploy/sms.sh
```

نام کاربری و **رمز وب‌سرویس** (پنهان تایپ می‌شود) و bodyId الگوها را می‌پرسد؛ فقط الگوی ورود لازم است و Enter مقدار فعلی را نگه می‌دارد (`-` حذفش می‌کند). `.env` با نسخهٔ پشتیبان عوض می‌شود، فقط `iphoneha-api` ری‌استارت می‌شود (اگر بالا نیامد، `.env` قبلی خودکار برمی‌گردد) و یک کد ورود واقعی به موبایلی که می‌گویی فرستاده می‌شود. الگوهای هشدار به کارکنان همچنان با `alerts.sh`.

الگوهای مشتری را در پنل ملی‌پیامک (الگوها ← الگوی جدید) با همین متن و همین ترتیب متغیرها بساز:

| الگو               | متن پیشنهادی                                                                                                           | کی فرستاده می‌شود                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| ورود (لازم)        | `کد ورود شما به آیفونی‌ها: {0}`                                                                                        | ورود و ثبت‌نام                             |
| سفارش موفق         | `آیفونی‌ها: سفارش {0} به مبلغ {1} تومان با موفقیت ثبت شد. پیگیری: iphoneha.com/account/orders`                         | پرداخت آنلاین موفق، و سفارش تلفنی یا حضوری |
| پرداخت سفارش       | `آیفونی‌ها: پرداخت سفارش {0} با موفقیت انجام شد.`                                                                      | فقط وقتی «سفارش موفق» نیست                 |
| ارسال              | `آیفونی‌ها: سفارش {0} ارسال شد. کد رهگیری: {1}`                                                                        | ثبت ارسال در پنل                           |
| صدور دفترچهٔ اقساط | `آیفونی‌ها: دفترچه اقساط قرارداد {0} صادر شد: {1} قسط {2} تومانی، اولین سررسید {3}. iphoneha.com/account/installments` | ثبت قرارداد چک یا سفته                     |
| پرداخت قسط         | `آیفونی‌ها: پرداخت قسط {0} قرارداد {1} به مبلغ {2} تومان ثبت شد. مانده: {3} تومان`                                     | ثبت پرداخت قسط یا وصول چک                  |
| یادآوری قسط        | `آیفونی‌ها: یادآوری قسط قرارداد {0} به مبلغ {1} تومان با سررسید {2}.`                                                  | چند روز پیش از سررسید، ساعت ۱۰             |
| قسط معوق           | `آیفونی‌ها: قسط قرارداد {0} به مبلغ {1} تومان از سررسید {2} پرداخت نشده است. لطفاً هرچه زودتر پرداخت کنید.`            | هر چند روز یک‌بار پس از سررسید             |

یادآوری و پیام معوق فقط وقتی می‌روند که «یادآوری خودکار» در پنل (تنظیمات ← دفتر اقساط) روشن باشد. اگر الگوی «قسط معوق» را نسازی، برای قسط‌های گذشته از سررسید همان الگوی یادآوری فرستاده می‌شود.

### هشدار درخواست و سفارش تازه (پیامک، تلگرام یا بله)

وقتی کسی فرم «خرید قسطی با چک یا سفته» را می‌فرستد یا سفارشی پرداخت می‌شود، فروشگاه خبرت می‌کند:

- **داخل پنل (همیشه روشن):** عدد کنار «درخواست‌های اقساط» هر دقیقه به‌روز می‌شود و درخواست تازه با یک پیام کوچک پایین صفحه اعلام می‌شود. با «روشن کردن اعلان مرورگر» در تنظیمات ← هشدارها، وقتی در زبانهٔ دیگری هستی هم اعلان سیستمی می‌آید.
- **پیامک:** با الگوهای تازهٔ ملی‌پیامک (جدول زیر).
- **ربات تلگرام یا بله:** رایگان و بدون الگو.

```bash
bash /home/iphoneha/app/deploy/alerts.sh
```

اسکریپت bodyId الگوها و توکن ربات را **همان‌جا در ترمینال** می‌پرسد. توکن موقع تایپ دیده نمی‌شود و جز به خود تلگرام یا بله جایی فرستاده نمی‌شود. گفتگوی ربات را خودش پیدا می‌کند (کافی است به ربات پیام بدهی)، فقط API را ری‌استارت می‌کند و سایت بالا می‌ماند، و از هر راه یک پیام آزمایشی می‌فرستد. هر وقت خواستی دوباره اجرایش کن تا چیزی را عوض یا حذف کنی.

| الگو                   | متن پیشنهادی                                                               | متغیرها                                                   |
| ---------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------- |
| درخواست تازه           | `آیفونی‌ها: درخواست خرید قسطی تازه، شماره {0} با {1}. در پنل پیگیری کنید.` | `{0}` شمارهٔ درخواست، `{1}` «چک صیادی» یا «سفته»          |
| سفارش پرداخت‌شده       | `آیفونی‌ها: سفارش {0} به مبلغ {1} تومان پرداخت شد.`                        | `{0}` شمارهٔ سفارش، `{1}` مبلغ                            |
| یادآوری قسط (به مشتری) | `آیفونی‌ها: یادآوری قسط قرارداد {0} به مبلغ {1} تومان با سررسید {2}.`      | `{0}` شمارهٔ قرارداد، `{1}` ماندهٔ قسط، `{2}` سررسید شمسی |

- **چه کسی پیامک می‌گیرد:** پنل ← تنظیمات ← هشدارها، تا سه موبایل. خالی یعنی موبایل مدیر اصلی. هر کدام از دو هشدار را همان‌جا می‌شود خاموش کرد و دکمهٔ «فرستادن پیام آزمایشی» پیامک و ربات را همان لحظه امتحان می‌کند.
- **چه چیزی فرستاده می‌شود:** شمارهٔ درخواست یا سفارش، روش پرداخت، مدل و مبلغ. نام و موبایل مشتری فقط در پنل است، چون پیام ربات روی سرورهای تلگرام یا بله می‌ماند.
- **سقف:** فرم درخواست عمومی است. در هر ساعت بیشتر از ۱۰ هشدار درخواست فرستاده نمی‌شود و بقیه فقط در پنل می‌آیند، تا فرم‌های جعلی هزینهٔ پیامک نسازند.
- این سرور در آمریکاست و تلگرام را می‌بیند. بله ممکن است به سرور خارج از ایران جواب ندهد؛ اسکریپت این را صریح می‌گوید.
- اگر کلید یا تنظیم هشدار اشتباه باشد، فقط همان هشدار نمی‌رسد و در لاگ نوشته می‌شود. فروشگاه هیچ‌وقت به‌خاطر آن از کار نمی‌افتد.
- **یادآوری قسط** برای مشتری‌های «دفتر اقساط» (فروش خود فروشگاه با چک و سفته) است و تا در پنل ← تنظیمات ← دفتر اقساط روشن نشود هیچ پیامکی نمی‌رود. روشن که شد، هر روز ساعت ۱۰ صبح به وقت تهران چند روز پیش از سررسید و هر چند روز برای قسط معوق پیامک می‌رود (روزی حداکثر یک بار برای هر قسط). دکمهٔ زنگ کنار هر قسط هم همان لحظه یک یادآوری می‌فرستد.

### خرید قسطی آنلاین: اسنپ‌پی، تارا، دیجی‌پی، باجت، ازکی‌وام

اتصال این پنج سرویس در فروشگاه آماده است و فقط کلیدهای پذیرندگی شما را لازم دارد. هر سرویس بعد از قرارداد این‌ها را می‌فرستد:

| سرویس                                 | چه چیزی بگیرید                                                                                                                                                             | IP سرور                                                                  |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| اسنپ‌پی                               | `client_id`، `client_secret`، `username`، `password` و کد `commissionType` قرارداد (اگر نگفتند، ۱۰۰)                                                                       | الزامی. `2.25.204.68` را هم برای کلید تست و هم برای کلید اصلی اعلام کنید |
| تارا (درگاه اعتباری تارا)             | نام کاربری و رمز عبور درگاه، و **کد درگاه** (serviceId). بعد از وصل شدن، اسکریپت فهرست «گروه‌های کالا»ی قراردادتان را نشان می‌دهد؛ کد گروه گوشی را در اجرای بعدی وارد کنید | اگر خواستند                                                              |
| دیجی‌پی (UPG، خرید اعتباری)           | `client_id`، `client_secret`، `username`، `password`                                                                                                                       | اگر خواستند                                                              |
| باجت (طرح اعتباری بانک تجارت، JETPAY) | `username`، `password` و شمارهٔ ترمینال (`terminalId`)                                                                                                                     | اگر خواستند                                                              |
| ازکی‌وام                              | شناسهٔ پذیرنده (merchant id) و کلید API، که ۶۴ کاراکتر است                                                                                                                 | اگر خواستند                                                              |

**نسیبا** هنوز وصل نمی‌شود: نسیبا API عمومی برای فروشگاه‌های اینترنتی منتشر نکرده و مستند فنی‌اش با قرارداد پذیرندگی می‌آید (ثبت‌نام پذیرنده: `app.nasiba.ir/merchant/signup`، پشتیبانی `support@nasiba.ir`، ۰۲۱-۹۱۳۰۲۲۸۸). وقتی مستند یا کلیدها رسید، کلاینتش مثل بقیه نوشته و با همین اسکریپت وصل می‌شود؛ تا آن موقع در سایت نمایش داده نمی‌شود.

اگر آدرس بازگشت (return URL یا callback) خواستند، دامنه `https://iphoneha.com` است. سایت برای هر پرداخت آدرس کاملش را زیر `https://iphoneha.com/api/payments/callback/` خودش می‌فرستد.

```bash
bash /home/iphoneha/app/deploy/installments.sh
```

اسکریپت برای هر سرویس می‌پرسد که نگه دارد، با کلید **اصلی** وصل کند (`l`)، با کلید **تست** وصل کند (`t`) یا خاموش کند (`o`). کلیدها **همان‌جا در ترمینال** تایپ می‌شوند، رمزها موقع تایپ دیده نمی‌شوند و فقط در `.env` سرور می‌مانند. بعد فقط API ری‌استارت می‌شود و هر سرویس از خود سرور و بدون هیچ خریدی امتحان می‌شود:

- **اسنپ‌پی:** ورود و یک استعلام «این مبلغ قسطی می‌شود؟»
- **تارا:** ورود و گرفتن فهرست گروه‌های کالای قرارداد (همان‌جا چاپ می‌شود تا کد گروه گوشی را انتخاب کنید)
- **دیجی‌پی:** ورود
- **باجت:** ورود با نام کاربری، رمز و شمارهٔ ترمینال
- **ازکی‌وام:** استعلام یک تراکنش ساختگی. جواب «پیدا نشد» یعنی شناسه و کلید درست‌اند.

**کلید تست.** بیشتر سرویس‌ها اول کلید محیط تست را می‌دهند و قبل از کلید اصلی یک خرید آزمایشی می‌خواهند. وقتی سرویسی با `t` وصل است:

- فقط به کارکنان فروشگاه نشان داده می‌شود، یعنی کسی که در **سایت** (نه پنل) با موبایل یک مدیر فعال وارد شده باشد. کنار اسمش «(آزمایشی)» نوشته می‌شود.
- هیچ صفحه‌ای از سایت آن را تبلیغ نمی‌کند و اگر مشتری مستقیم درخواستش را بفرستد، رد می‌شود. دلیلش این است که پرداخت محیط تست بدون پول واقعی تأیید می‌شود.
- بعد از خرید آزمایشی، سفارش را در پنل لغو کنید. این کار برگشت پول را هم امتحان می‌کند.
- آدرس محیط تست اسنپ‌پی و دیجی‌پی خودکار انتخاب می‌شود. ازکی‌وام محیط تست جدا ندارد و کلید تستش روی همان آدرس اصلی کار می‌کند. تارا و باجت محیط تست عمومی ندارند: اگر خودشان آدرس تست دادند، با `t` همان آدرس را وارد کنید؛ اگر نه، مستقیم با `l` وصل کنید.

وقتی کلید اصلی رسید، اسکریپت را دوباره اجرا کنید و `l` را بزنید. از همان لحظه سرویس در صفحهٔ پرداخت، ماشین‌حساب اقساط و استوری‌های صفحهٔ اصلی به مشتری‌ها نشان داده می‌شود. تعداد قسط، پیش‌پرداخت و سقف هر سرویس را در پنل ← تنظیمات ← پرداخت تعیین کنید.

**ایمنی.**

- سفارش فقط وقتی «پرداخت‌شده» می‌شود که خود سرویس پرداخت را تأیید کند. داده‌هایی که مرورگر مشتری برمی‌گرداند فقط یک نشانه‌اند:
  - اسنپ‌پی: `verify` و بعد `settle`
  - تارا: `purchaseVerify` که باید برای همان توکن، `rrn` و همان مبلغ را برگرداند (تارا پرداخت تأییدنشده را خودش برمی‌گرداند)
  - دیجی‌پی: `verify` با کد پیگیری، که سرویس باید همان پرداخت و همان مبلغ را برایش برگرداند
  - باجت: `inquiry` روی شمارهٔ مرجع خودمان و بعد `verify`، که باید تا ۱۵ دقیقه انجام شود (سایت همان لحظهٔ بازگشت مشتری این کار را می‌کند و اگر مشتری برنگشت، قبل از انقضای سفارش)
  - ازکی‌وام: `verify` تیکت
- مشتری تارا اول به یک صفحهٔ کوچک روی خود سایت (`/api/payments/go/…`) می‌رود که او را با فرم به تارا می‌فرستد؛ این طبیعی است، چون تارا لینک پرداخت ندارد.
- اگر مشتری پرداخت کرده ولی به سایت برنگشته، قبل از لغو سفارش وضعیتش از سرویس پرسیده می‌شود.
- کلید تست هیچ‌وقت با سوییچ «اصلی» کار نمی‌کند. اگر آدرس یک محیط تست (staging، sandbox، uat و…) کنار `live` باشد، آن سرویس اصلاً ارائه نمی‌شود.
- کلید ناقص یا اشتباه فقط همان سرویس را از صفحهٔ پرداخت برمی‌دارد و در لاگ API نوشته می‌شود. فروشگاه به‌خاطرش از کار نمی‌افتد.

**بعد از فروش.**

- **دیجی‌پی:** خرید اعتباری دیجی‌پی بعد از تحویل تسویه می‌شود. وقتی سفارش را در پنل «تحویل شد» می‌کنید، سایت خودش به دیجی‌پی خبر می‌دهد.
- **برگشت پول:** لغو سفارش پرداخت‌شده در پنل، کل مبلغ را از همان سرویس برمی‌گرداند (اسنپ‌پی، دیجی‌پی، ازکی‌وام). **تارا و باجت API برگشت ندارند:** پرداخت در پنل «در انتظار بازپرداخت» می‌ماند و مبلغ را باید از پنل پذیرندگی همان سرویس برگردانید. برگشت بخشی از مبلغ را همیشه از پنل خود سرویس انجام دهید.

**اگر اسکریپت نوشت `no answer`:** سرویس به این سرور جواب نداده است. اول IP سرور را به سرویس بدهید. اگر فقط به سرورهای داخل ایران جواب می‌دهد، راه‌های بخش «سرویس‌های ایرانی از سرور خارج» (بالاتر) اینجا هم کار می‌کنند.

## مرحله ۸ — پشتیبان‌گیری و چرخش لاگ

`bootstrap-root.sh` هر دو را خودش نصب می‌کند:

- `/etc/cron.daily/iphoneha-backup`: هر شب یک دامپ دیتابیس، تصاویر محصولات و یک نسخه از `.env` در `/home/iphoneha/backups` می‌گیرد، فقط برای root قابل خواندن است و ۱۴ روز نگه داشته می‌شود.
- `/etc/logrotate.d/iphoneha`: لاگ‌ها روزانه چرخانده و ۱۴ روز نگه داشته می‌شوند.

```bash
bash /home/iphoneha/app/deploy/backup.sh     # یک بار دستی تست کن
```

بکاپ فقط روی همین سرور است. برای امنیت بیشتر، هر چند وقت یک بار آخرین فایل `db_*.dump` را جای دیگری هم نگه دارید.

## به‌روزرسانی بعدی

بستهٔ جدید `iphoneha-deploy.tar.gz` را در `/home/iphoneha/` آپلود کن (با تیک Overwrite)، بعد با **root** همان دو خط نصب را بزن:

```bash
tar xzf /home/iphoneha/iphoneha-deploy.tar.gz -C /tmp iphoneha/deploy/bootstrap-root.sh --strip-components=2
bash /tmp/bootstrap-root.sh
```

`.env`، تصاویر آپلودشده و داده‌های دیتابیس دست نمی‌خورند؛ فقط کد عوض می‌شود، مهاجرت‌های جدید اجرا می‌شوند و سرویس‌ها ری‌استارت می‌شوند.

در هر به‌روزرسانی دو همگام‌سازی هم خودکار اجرا می‌شود:

- `catalog:sync` مدل‌ها، رنگ‌ها و عکس‌های رسمی تازهٔ نسخه را اضافه می‌کند و به قیمت، موجودی و متن‌های مدیر دست نمی‌زند.
- `content:sync` مقاله‌های مجله‌ای را که نسخه برای اولین بار عرضه می‌کند منتشر می‌کند. مقاله‌ای که مدیر ویرایش یا حذف کرده، بازنویسی یا برگردانده نمی‌شود.

## برگرداندن همه‌چیز (اگر لازم شد)

```bash
systemctl disable --now iphoneha-api iphoneha-web
rm -f /etc/systemd/system/iphoneha-{api,web}.service /etc/sudoers.d/iphoneha-app
rm -rf /etc/nginx/conf.d/users/iphoneha/iphoneha.com
rm -rf /etc/apache2/conf.d/userdata/{std,ssl}/2_4/iphoneha/iphoneha.com
systemctl daemon-reload; nginx -t && systemctl reload nginx
/scripts/ensure_vhost_includes --user=iphoneha; systemctl restart httpd
cd /home/iphoneha/app && docker compose -f deploy/docker-compose.data.yml down -v
```

سرور دقیقاً به وضعیت قبل برمی‌گردد و سه سایت دیگر هیچ‌وقت درگیر نمی‌شوند.
